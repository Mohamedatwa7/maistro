## 6.2 Moodboard — what ships (and a correction from verification)

- Visual direction: schema-validated structure from Claude (`api/_studio/mood.js`, prompt `mood-direction-v1`), palette hexes from the brand KB, the catalog look line as the only product fact, four tile briefs, competitor names rejected.
- The rendered set: ONE Soul V2 job with `batch_size 4`. **Correction (checker finding, 2026-10-21):** a Soul batch renders one prompt as variations, so the set is now rendered from a direction-level `setPrompt()` (setting, product when in the catalog, lighting, styling, palette) and every image is tagged `variation n` with `setMode: 'variations'` on the artifact. The earlier build rendered tile 1's prompt four times while tagging the images with tiles 1–4 and holding only "product" tiles to the product check — the tags claimed facets that were never asked for. The four tile briefs stay on the direction as text for the human. One job per tile (four submits) remains an option if the owner wants one image per facet.
- The product is expected in every variation exactly when the catalog has a look line (`meta.expectProduct`, explicit on the job); the vision check (`vision-check-v1.1`) stores a `stage_checks` row per set.
- Ops fixes from verification: the `vision_check` claim window is 150 s (above the 90 s call bound, so a second tick cannot re-claim a running check) and the job is patched to `running` before the call; vision `max_tokens` 8000; studio default model `claude-opus-5-5` (`MAISTRO_STUDIO_MODEL`).

| Aspect | `aspectFor(platforms)`: 9:16 unless a landscape platform (YouTube, X, Facebook) is targeted; `1152x2048` on Soul | TikTok/Reels covers are vertical. 4:5/1:1 for the Instagram feed is a follow-up once the feed is a selectable placement. |

| Checks | The vision check receives the selected mood tiles as ANCHOR images and the reserved side: `consistentWithMood` and `textSpaceClear` per image, flags `inconsistent with the moodboard` / `reserved text side is not clear`, plus the product-accuracy and safety questions | Consistency with the approved direction is judged against the actual approved pixels |
| Gate | 409 `prerequisites` when the piece has no moodboard version | No cover without a direction |

## 6.4 Brief — what ships

| Decision | What | Why |
|---|---|---|
| Inputs | `briefContext()` (`api/_studio/brief.js`): the moodboard's current version + its approval (selected tiles, annotations), the thumbnail's current version (headline = hook line), the piece's trend (board entry from `trends_cache` + the latest judgement from `trend_scores`), the catalog entry (look, features, colours, availability, **approvedClaims**), the GCC market context, the platform rules, the brand voice and do/don't lists | The brief is written only from what earlier stages produced and what the KB says; nothing is invented |
| Output | One schema-validated object, every field required: objective + success metric, audience + markets, trend hook + Samsung adaptation, key message, products with features, claims (claim / approved wording / disclaimer), CTA, tone, format (platform, format, aspect, target duration), language plan (on-screen, voice/captions, register gulf_arabic·msa·english·bilingual, rationale), audio (direction, music reference, licensing none·cleared·unknown), mandatories, do-nots, hashtags en/ar, caption en/ar, deadline | The spec's field list, as a contract the storyboard and QC can check against |
| Stored artifact | Legacy page fields (objective, msg, markets, platforms, mandatories, deadline) + `spec` (the structured brief) + `briefVersion`, `moodApproved`, `thumbApproved`, `editedBy` | The Hermes/storyboard paths keep working; the structured spec is additive |
| Code checks (`codeChecks()`) | `product_in_catalog`, `claims_approved` (every claim's approved wording must appear in the catalog's `approvedClaims` — with the list empty today, **any claim fails**, so the model is told to make none), `duration_sweet_spot` (builder defaults tiktok 9–30 s, reels 7–15 s, feed 5–60 s, stories 5–15 s; KB `organic.sweetSpotS` overrides), `hashtag_limit` (≤ 5, ≤ 3 stories/YouTube), `audio_licensed` (a named track must be `cleared`), `arabic_copy_present` (Gulf markets need an Arabic caption and hashtags), `mandatories_complete` (hero product, logo end-frame, audio rule), `deadline_realistic` (today → +14 d) | Numbers and mappings are computed in code, never by the model |
| Copy check | One Sonnet call (`brief-copy-check-v1`, effort low): Arabic fluency native · mostly_native · literal · n/a with the phrases that read as translated; consistency with the moodboard direction; whether the hook uses the trend's actual mechanic | The three checks the spec asks for that need reading, kept as flags for the human |
| Storage | `stage_checks` kind `copy` on the version: `{codeChecks[], copy, flags[], passed}`; `passed` = every code check and no literal Arabic / mood contradiction / missing mechanic | Same table and page badges as the vision checks |
| Human edits | "Edit fields" on the page → `action: 'brief-edit'` → the edited spec is validated, stored as a **new manual version**, re-checked (code + copy), never overwritten | The spec's "edit fields directly, saved as a new version" |
| Gate | 409 `prerequisites` without a moodboard; the moodboard's approval state is recorded, not enforced (builder default — owner to amend) | Keeps the demo flow usable before the first sign-off |

Open: approved claims per device (owner input 2) — until they exist the brief carries no verifiable product claim; per-platform sweet spots unverified; the copy check is a flag, not a fluency guarantee (a native reviewer still signs).

## 6.5 Storyboard — what ships

| Decision | What | Why |
|---|---|---|
| Inputs | The brief stage's current version (`briefFor()`, approval state recorded), the moodboard direction + the reviewer's selected tiles and annotations (`moodContext()`), the trend judgement / board entry, the catalog look line, the cultural rules | The shot list is written from the approved brief and nothing else |
| Shot list | `storyboard-v1` (`api/_studio/board.js`), 3–8 shots, each: `n`, `durationS`, `type` (wide · medium · close_up · macro · pov · insert · end_card), `camera` (angle + movement), `action`, `product{visible, feature}`, `onScreenText{en,ar}`, `line{en,ar}`, `audioCue`, `transition` (cut · match_cut · whip · dissolve · hold · none); plus `hookShot` and a note | The spec's per-shot fields, as data the video stage can consume one shot at a time |
| Code checks (`codeChecks()`) | `duration_matches_brief` (sum within ±10 % of the brief's target), `hook_in_first_seconds` (hook shot starts < 3 s), `features_covered` (every brief feature shown in a product-visible shot), `key_message_present`, `cta_at_end` (last two shots), `end_card` (last shot is an end card naming the logo), `product_visible` | Arithmetic and coverage never left to the model |
| Mechanic check | One Sonnet call (`storyboard-check-v1`, effort low): `followsTrendMechanic` + missing beats, `hookStrength` strong · ok · weak, brand risks | The "recognisable as the trend" and "weak hook" judgements the spec asks for, kept as flags |
| Storage | The version payload holds `shots[]` with an empty `keyframe` and `review` per shot; checks in `stage_checks` kind `spec` | One storyboard version; keyframes fill it in |
| Keyframes | One Soul job per shot through the job service (`payload.attachTo = {versionId, shot}`), `keyframePrompt()` from the shot + direction + catalog look, 9:16 at 1080p, the official product photo through the v1 reference path when the product is visible; `attachKeyframe()` copies the asset into the private bucket and writes `shots[n-1].keyframe` (previous keyframe kept in `keyframeHistory`), **the version number does not change**; the stage is `generating` while any render job lives and returns to `generated` when the last one lands (`settleBoardStage()`); a failed render marks only its shot | Per-shot rendering and per-shot regeneration without a new version per keyframe |
| Checks per keyframe | A vision check per keyframe with the selected mood tiles **and the previous shot's keyframe** as anchors (cross-shot consistency: same product, character, setting, lighting), `expectProduct` = the shot's `product.visible`; F1X8 image analysis on the hook shot's keyframe (`hookCheck`), stored in `qc_results` on the storyboard version and shown as the hook score | The spec's product-per-keyframe, cross-shot consistency and lightweight F1X8 checks |
| Review | `board-shot-decide` records `shots[n].review` (approve needs a rendered keyframe; reject needs a reason + taxonomy code), audit-logged; `board-shot` re-renders ONE shot (409 `busy` while it renders, 409 `approved_immutable` after the stage approval); the stage approval (`POST /api/decisions`) is refused with 409 `shots_pending` until every shot is approved (also pre-checked on the page) | "Per shot. Only rejected shots regenerate." |
| Page | `rBoard()`: shot cards with the keyframe (signed from the private copy), state, check and review badges, text/line (RTL Arabic), audio, transition; Approve / Reject (reason + code) / Regenerate per shot; `boardPoll()` refreshes the version as keyframes land | Reviewers see each shot arrive and act on it alone |

Open: Higgsfield consistency features (Soul ID / custom references, HIGGSFIELD.md) are not used yet — consistency is asserted by the prompt anchors and checked by vision, not enforced by the model; the end card is a rendered placeholder until the logo/end-card rules arrive (owner input 1); keyframe prompts carry no seed (Soul V2 accepts one — a follow-up for reproducible re-renders).

## 6.6 First draft — part (a): clips (what ships)

| Decision | What | Why |
|---|---|---|
| Gate | `action: 'draft'` needs the storyboard's current version with every shot **reviewed approved and rendered** (409 `prerequisites` with the pending shot numbers); the storyboard stage approval is recorded as `boardApproved` | "Turn approved keyframes into a real video" — nothing else |
| Model | Seedance 2.5 **image-to-video** (`bytedance/seedance-2.5/image-to-video`, HIGGSFIELD.md §2.2): `image_url` = the shot's keyframe, `prompt` = the shot's camera movement + action in present tense (product shots add "the device stays exactly as in the first frame"), `duration` = the shot's duration clamped to Seedance's 4–30 s (the assembly trims to the shot), `resolution` (default 720p, 1080p selectable), `generate_audio: true`, `bitrate_mode: high`; no `aspect_ratio` (the keyframe sets the framing) | One clip per approved shot with its keyframe as the image input |
| Jobs | One `higgsfield_video` job per shot with `payload.attachTo = {versionId, shot}` and `imageAssetPath` (the private keyframe); at first submit the job service mints ONE signed URL (24 h) and stores it on the job so the idempotent body is byte-identical on retries (same key + different body would be Higgsfield's 422); clips attach to `shots[n].clip` through `updateShots()` (previous clip → `clipHistory`, review reset); the draft stage is `generating` until the last clip lands, then `generated`; a failed clip marks only its shot; generation records carry `seed: null` (Seedance has no seed) | Background, per shot, never a serverless timeout, status per shot on the page |
| Draft version | One version per draft run: `shots[]` (shot fields + `keyframe` ref + `clipDurationS` + `clip` + `review`), `totalS`, `aspect`, `resolution`, `boardVersionId`; legacy fields (`version`, `dur`, `audio`, `variants`, `videoUrl: null`) kept so the legacy renderer and QC keep working; `assembled: null` until part (b) | The version is the unit of approval; clips fill it in |
| Review | `shot-decide` with `stage: 'draft'` (approve needs a rendered clip; reject needs a reason); `draft-shot` re-renders ONE clip with the reviewer's changes appended (409 `busy` while rendering, 409 `approved_immutable` after the stage approval) | "A rejected shot regenerates alone" |
| Page | `rDraft()`: per-shot clip players (signed from the private copy), states, review badges, Approve / Reject / Re-render per clip, the overlay text each shot will get at assembly; `shotsPoll(pid, 'draft')` refreshes as clips land | Status visible per shot |

Not yet (part b, next): assembly (ordering and trimming to exact shot durations, transitions, code-rendered overlays with Arabic shaping, captions, loudness, logo/end card, per-platform export) and the per-clip checks (product stability / no morphing, artifacts, consistency with the keyframe) which need frames extracted from the clips — both require ffmpeg in the function (design: `ffmpeg-static` bundled with `includeFiles`, an `assemble` job kind, overlay PNGs drawn in the browser as for the thumbnail).
